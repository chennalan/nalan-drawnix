# Drawnix cloud autosave (test-first)

The cloud autosave implementation is wired to the Drawnix UI on the `feature/cloud-autosave` branch. It is **not production-ready until the Pages deployment is protected by Cloudflare Access, the two Access values are configured, and CI/runtime tests pass**.

## Architecture

- Drawnix continues writing to browser local storage through localforage immediately.
- The UI provides a cloud panel to check connection, create a cloud copy, restore a listed cloud document, and pause syncing.
- After a cloud document is selected or created, subsequent board edits are debounced and saved to the selected document.
- Cloud API calls are same-origin through `functions/api/documents/[[id]].ts`; this avoids cross-origin browser credentials and permissive CORS.
- Cloudflare Access must protect `nalan-drawnix.pages.dev`. The Pages Function passes the request to the API, which cryptographically validates the Access JWT and scopes every document query to its verified subject.
- D1 stores metadata; the private R2 bucket stores document JSON. The UI does not silently replace local content with cloud content: restore requires confirmation. Revision conflicts are reported and do not overwrite the other revision.

## Preview deployment watch paths

The Pages project watches the application source, Pages Functions, cloud API/configuration, and build manifests so changes to this feature trigger preview deployments.

## Dedicated test resources

- D1: `nalan-drawnix-test`
- R2: `nalan-drawnix-documents-test`

The root `wrangler.toml` binds only these dedicated test resources. Never bind this project to `nalan-work`, `nalan-mindmap`, or `nalan-backup`.

## Required before deployment

1. Configure Cloudflare Access for `https://nalan-drawnix.pages.dev` and restrict it to the intended user(s).
2. Set `ACCESS_TEAM_DOMAIN` and `ACCESS_AUD` in the Pages environment to the exact Access team domain and application audience. Do not leave the placeholders in `wrangler.toml`.
3. Verify that Access login is enforced before the Pages app and API can be reached. Do not expose the Worker API separately without equivalent Access enforcement.
4. Run the web build and inspect deployment logs. Then test: anonymous request rejected, logged-in request succeeds, user isolation, create/save/reopen, revision conflict, oversized payload rejection, and offline/local recovery.
5. Only then merge and deploy. Production should use separately reviewed production resources, not the test D1/R2 bindings.

## Security behavior

- Identity is taken only from a cryptographically verified Access JWT; browser-supplied owner IDs are ignored.
- D1 ownership checks include the verified JWT subject.
- R2 object keys are generated by the API and the bucket must remain private.
- Payload size is capped at 2 MiB.
- Local browser saving remains available if cloud login or the API is unavailable.
